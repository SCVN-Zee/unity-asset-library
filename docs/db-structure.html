Database structure & entity relationships.

No SQL database. Package archives stay in the library; persistent state lives in <library>/.data/. Each package uses a stable asset_key across the index, cache, and user annotations.

01 / Storage overview

Keep versus rebuild

Keep: identities, tags, favorites, preferences, and manual overrides. The registry preserves ownership beyond the current scan.

Rebuild: inventory from archives plus the retained registry; store cache through fresh lookups; pending work from current inventory and cache.

References may remain after a package is absent. Cardinalities describe a current package, not automatic cascading deletion.

Recovery is not a full backup

storage-journal.json coordinates multi-file index/identity migration with temporary stage and backup files.

identity-migration-backup.json retains original legacy index, annotations, cache, and overrides during identity cutover.

Shared file locks serialize local mutations. Atomic replacement protects individual writes. The migration snapshot is not an ongoing user-data backup.

Supporting files

.data/config.json and index-meta.json: library configuration and index metadata.

assets.csv, review-queue.md: generated exports.

The repository’s config.json only points to the last-opened library. Import staging is disposable, not a persistent package cache.

03 / User-data ERD

TagAssignment makes the package–tag many-to-many relationship explicit. LibraryPreferences is independent of package identity.

Cardinality scope

The first view shows records associated with a currently indexed package. Persistent identity, annotations, cache, and override records can outlive its current Package projection. There is no automatic cascading deletion. Multiple package identities can reference the same store ID without merging.

Supporting storage, not domain entities

Configuration, index metadata, generated CSV/review reports, locks, the recovery journal, and migration backups are omitted from this ERD. Their storage roles are shown in the database structure diagram. No account/user table or SQL migration is implied.
